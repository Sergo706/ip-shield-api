# IP Shield API

**IP intelligence and threat detection as a single HTTP call.**

IP Shield is a self-hosted IP intelligence platform. It answers questions about an
incoming request — _is this a VPN, a residential proxy, a Tor exit node, a verified
crawler, a disposable email domain, a scanner user-agent, where is it located, which
network does it belong to_ — in single-digit milliseconds, without DNS lookups or
third-party API round-trips.

All lookups are resolved from binary databases ([MMDB](https://maxmind.github.io/MaxMind-DB/)
format and [LMDB](https://www.symas.com/lmdb)) held in process memory, so the hot path
never leaves the machine. The datasets themselves are generated by my own modules —
see [Ecosystem](#ecosystem) below.

## What is in this repo

| Path                | What it is                                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/core`         | The **API + dashboard** (Nuxt 4 / Nitro). Public `/api/v1/*` endpoints, user auth, API key management, quota and rate limiting, playground, billing models. |
| `apps/static`       | The **marketing site and documentation** (Nuxt Content, statically generated). Not required to use the API.                                                 |
| `apps/shared/layer` | Shared Nuxt layer: UI components, composables, shared Zod schemas and types used by both apps.                                                              |
| `docker/`           | Hardened images: gateway, app, database, tunnel, log shipper, auto-updater.                                                                                 |
| `scripts/`          | Developer tooling: secret encryption/decryption, local and production start scripts.                                                                        |
| `config.alloy`      | Grafana Alloy pipeline that ships container and host logs/metrics to Loki/Prometheus.                                                                       |

> **Note:** the authentication service itself is _not_ in this repository — it is
> consumed as a prebuilt image (`sergio68/auth:latest`) and reached over an
> HMAC-authenticated channel. See [IAM](https://docs.riavzon.com/docs/iam). You only
> need the client credentials listed below to run the core app.

## Ecosystem

IP Shield is the product that ties together a set of modules I maintain separately.
Each one is documented, versioned, and reusable on its own:

| Module            | Role here                                                                                                   | Docs                                          |
| ----------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **auth-h3client** | Client side of the auth handshake; the app talks to the auth service through it                             | <https://docs.riavzon.com/docs/auth-h3client> |

| **shield-base**   | Builds, compiles, and refreshes the MMDB/LMDB datasets that this API serves from                            | <https://docs.riavzon.com/docs/shield-base>   |

## Features

### Endpoints

| Purpose                                                           | Route                                    |
| ----------------------------------------------------------------- | ---------------------------------------- |
| Full intelligence summary (geo + network + threat in one payload) | `GET /api/v1/summary/{ip}`               |
| Full IP profile                                                   | `GET /api/v1/lookup/ip/{ip}`             |
| Network / ASN / proxy / VPN / Tor / verified-bot data             | `GET /api/v1/network/{ip}`               |
| City-level geolocation                                            | `GET /api/v1/check/geo/{ip}`             |
| Disposable email domain check                                     | `GET /api/v1/check/email-domain/{email}` |
| Malicious user-agent / scanner detection                          | `GET /api/v1/check/user-agent/{agent}`   |
| Health probe                                                      | `GET /health`                            |

Every response is JSON in the shape:

```json
{
  "ok": true,
  "date": "2026-01-01T00:00:00.000Z",
  "data": {},
  "meta": { "credits_remaining": 999, "total_credits": 1000 }
}
```

Errors return `ok: false` with a machine-readable `error.code`, `error.message` and
`error.details`.

### Platform

- **API keys** — create, rotate, revoke; optional expiry date and IP allowlist per key.
- **Quotas + rate limits** — per-plan monthly quota and per-minute limits, with
  `Retry-After` on `429`. Escalating penalty for clients that ignore it.
- **Auth** — email/password with confirmation, password reset, email change, MFA,
  plus Google and GitHub OAuth. Session cookies are signed, CSRF protected, and the
  browser client talks to the auth service over an HMAC-authenticated channel
  ([auth-h3client](https://docs.riavzon.com/docs/auth-h3client) +
  [IAM](https://docs.riavzon.com/docs/iam)).
- **Plans and billing models** — `free` / `pro` / `custom` seeded in the database;
  requests-per-minute, monthly quota, feature flags, and price rows are data, not code.
- **Playground** — test any endpoint from the dashboard against live data with your
  own quota.
- **Background refresh** — a scheduled job rebuilds the local databases via
  [shield-base](https://docs.riavzon.com/docs/shield-base) on a configurable interval,
  then atomically swaps them in.
- **Structured logging** — separated HTTP / info / warn / error streams, plus
  container and host telemetry shipped to a central Loki instance.

### Data sources

| Domain      | Source                                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Geo / ASN   | Country, city, and ASN datasets compiled by [shield-base](https://docs.riavzon.com/docs/shield-base) from RIR geofeeds and enrichment data                                                                                                 |
| Threat      | FireHOL level 1–4 and anonymous blocklists, **plus threat actors harvested by [bot-detection](https://docs.riavzon.com/docs/bot-detection) on honeypot sites and production apps I run** — these are periodically compiled into new MMDBs. |
| Anonymity   | Tor exit node list, VPN and residential-proxy ranges                                                                                                                                                                                       |
| Bots        | Verified crawler ranges (Google, Bing, OpenAI, …)                                                                                                                                                                                          |
| User agents | LMDB of known malicious scanners and tools, generated by [bot-detection](https://docs.riavzon.com/docs/bot-detection)                                                                                                                      |
| Email       | LMDB of disposable / temporary email domains                                                                                                                                                                                               |

Databases are read-only at runtime, memory-mapped, and hot-swappable. The application
starts with whatever is present in the data directory and refreshes on schedule; it
does not need network access to serve requests.

The threat layer is the part that is not resold commodity data: every request the
[bot-detection](https://docs.riavzon.com/docs/bot-detection) module scores on my own
sites feeds back into the dataset, so coverage of new actors improves over time rather
than at the vendor's publish cadence.

## Architecture

Request path, outer to inner:

```
Cloudflare edge
      │
      ▼
Tunnel container        no inbound ports on the host
      │
      ▼
Gateway                 TLS termination, caching, per-route rate limits, ban policy
      │
      ├── /api/* /dashboard* /auth*  ──▶  Core app (Nuxt / Nitro)
      │                                        ├── MySQL          (internal network)
      │                                        ├── MMDB + LMDB    (in-memory)
      │                                        ├── IAM            (HMAC channel)
      │                                        └── Log shipper
      │
      └── everything else            ──▶  Static site (pre-rendered)
```

Design notes:

- The host exposes **no public ports**. Ingress is entirely through an outbound tunnel,
  and the origin is reachable only from the private network.
- The gateway is the only component allowed to bind a privileged port. It normalizes
  client IP headers, strips identifying response headers, applies per-route rate limit
  zones, and issues temporary bans for repeat offenders.
- The application container runs **read-only**, as a non-root UID, with all
  capabilities dropped, a small `tmpfs` scratch space, and PID limits.
- Secrets never live in the image or in the compose file. They are `age`-encrypted at
  rest, decrypted at container start into a tmpfs, and handed to the process through
  the compose `secrets` mechanism.
- The database is on an `internal: true` network with no route to the internet.
- Images are rebuilt and pushed by CI on every push to `main`, and a watchtower
  container rolls them out.

## Quick start (local development, no containers)

### Prerequisites

- Node.js 22+ and [pnpm](https://pnpm.io) 10.30+
- MySQL 8
- An IP database set in `apps/core/data-sources/`

### 1. Install

```bash
pnpm install
```

### 2. Environment

Create `apps/core/.env`:

```dotenv
NODE_ENV=development
DOMAIN=localhost

DB_HOST=127.0.0.1
DB_PORT=3306
MYSQL_USER=ipshield
MYSQL_PASSWORD=change-me
MYSQL_DATABASE=ipshield

# Auth service
AUTH_SERVER_LOCATION=127.0.0.1
AUTH_PORT_LOCATION=4000
AUTH_CRYPTO_COOKIES=change-me
HMAC_CLIENT_ID=change-me
HMAC_SHARED_SECRET=change-me

# OAuth
OAUTH_GOOGLE_CLIENT_ID=
OAUTH_GOOGLE_CLIENT_SECRET=
OAUTH_GITHUB_CLIENT_ID=
OAUTH_GITHUB_CLIENT_SECRET=

# Captcha + email
NUXT_TURNSTILE_SECRET_KEY=
RESEND_API_KEY=

# Optional
CLIENT_LOG_DIR=./app-logs
DATA_SOURCES_DIR=./data-sources
DATA_RESET_SCHEDULE=86400000
```

| Variable                                     | Required         | Purpose                                   |
| -------------------------------------------- | ---------------- | ----------------------------------------- |
| `DB_HOST`, `DB_PORT`, `MYSQL_*`              | yes              | MySQL connection                          |
| `AUTH_SERVER_LOCATION`, `AUTH_PORT_LOCATION` | yes              | Where the auth service listens            |
| `AUTH_CRYPTO_COOKIES`                        | yes              | Cookie signing key                        |
| `HMAC_CLIENT_ID`, `HMAC_SHARED_SECRET`       | yes              | HMAC channel between app and auth service |
| `OAUTH_GOOGLE_*`, `OAUTH_GITHUB_*`           | for social login | OAuth clients                             |
| `NUXT_TURNSTILE_SECRET_KEY`                  | for forms        | Cloudflare Turnstile                      |
| `RESEND_API_KEY`                             | for email        | Transactional email                       |
| `DATA_SOURCES_DIR`                           | no               | Where the MMDB/LMDB files live            |
| `DATA_RESET_SCHEDULE`                        | no               | Refresh interval in ms (default 24h)      |

### 3. Databases and data files

Put the MMDB/LMDB set into `apps/core/data-sources/`:

```
data-sources/
├── asn.mmdb, city.mmdb, country.mmdb
├── proxy.mmdb, tor.mmdb, goodBots.mmdb
├── firehol_anonymous.mmdb, firehol_l1..l4.mmdb
├── useragent-db/
└── email-db/
```

These are built and refreshed by
[shield-base](https://docs.riavzon.com/docs/shield-base). If the directory is empty the
app still boots, but lookups return empty results.

### 4. Migrate

```bash
pnpm --filter @app/core migrate
pnpm --filter @app/core seed:plans
```

`migrate` runs `drizzle-kit generate` + `drizzle-kit push`; `seed:plans` inserts the
default plan rows.

### 5. Run

```bash
pnpm dev:core     # API + dashboard  → http://localhost:3001
pnpm dev:static   # marketing/docs   → http://localhost:3000
pnpm dev:both     # both, in parallel
```

Then create a key from `/account`, and call the API:

```bash
curl "http://localhost:3001/api/v1/summary/1.1.1.1" -H "x-api-key: YOUR_KEY"
```

### Useful scripts

| Command                                  | What it does                 |
| ---------------------------------------- | ---------------------------- |
| `pnpm build:core` / `pnpm build:static`  | Production builds            |
| `pnpm typecheck:core` / `pnpm lint:core` | Types and lint for one app   |
| `pnpm generate:static`                   | Fully static site generation |

## Running with containers

The containers are the supported way to run this the way it is deployed.

### Development

```bash
sh scripts/start-core.dev.sh
```

This builds the dev images, runs migrations and plan seeding, then starts the stack
with `docker compose up --watch` so source changes sync into the container.

Plain compose equivalents:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml build
docker compose run --rm migrations sh -c \
  "pnpm --filter @app/core migrate && pnpm --filter @app/core seed:plans"
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --watch
```

### Production-style

```bash
npx zx scripts/start-core.mts
```

What that script does, in order:

1. Encrypts every plaintext file under `secrets/app/env/`, `secrets/app/mysql/`,
   `secrets/auth/`, and `secrets/watchtower/` with `age`, writing `.age` siblings.
2. Deletes the plaintext copies (except `*dev*` files, which are kept for local use).
3. `chgrp -R 10001 secrets/` and `chmod -R g+rX secrets/` so the containers (UID 10001) can read them.
4. Creates `auth-logs/server/bot-detector`, `auth-logs/core-app`, and
   `apps/core/data-sources`, and hands them to UID 10001.
5. `docker compose build` for the main stack, then for the `migrations` image.
6. Runs `drizzle-kit generate && push` and `seed:live` inside the throwaway
   `migrations` container.
7. `docker compose up -d --force-recreate`.

If you prefer to drive it by hand:

```bash
docker compose build
docker compose build migrations
docker compose run --rm migrations \
  sh -c "pnpm --filter @app/core migrate && pnpm --filter @app/core seed:live"
docker compose up -d --force-recreate
```

> `scripts/start-core.mts` hardcodes `/home/sergio/src` and calls `sudo`. Edit the
> paths (and drop the `sudo`) before running it on a machine that is not mine. See
> [Self-hosting checklist](#self-hosting-checklist).

### Verify it came up

```bash
docker compose ps                    # every service should be healthy/running
docker compose logs -f dashboard     # Nitro boot + data-source load
curl -s http://localhost:3000/health  # inside: the app answers on 3000
docker compose exec dashboard node /app/docker/healthcheck.js
```

Note that the gateway deliberately answers `404` for `/health` (it is in the
`@blocked` matcher), so probe through the container, not through Caddy.

## Self-hosting checklist

This repo is my deployment, not a generic distribution. Several files contain values
that only work on my infrastructure. Everything below must be changed before the
stack will run correctly (or at all) on your machine.

### 1. Data sources (required)

`apps/core/data-sources/` must contain the MMDB/LMDB set. It is not in the repo
(`.gitignore` excludes `data-sources`). Generate it with
[shield-base](https://docs.riavzon.com/docs/shield-base) or copy an existing set.
Without it the API boots and returns empty payloads, and the scheduled refresh in
`02.scheduler.ts` throws `No data to restart, please first run the installation
wizard`.

The dashboard container mounts this directory from an absolute host path:

```yaml
- /home/sergio/src/apps/core/data-sources:/app/data-sources:rw
```

Change it to wherever your data lives. If the container should write there, the
directory must be owned by UID `10001`.

### 2. The auth service image

`docker-compose.yml` pulls `sergio68/auth:latest` from Docker Hub. The service is not
in this repo. Either get access to that image, or point `auth.image` at your own build
of [IAM](https://docs.riavzon.com/docs/iam). If you build your own, its encrypted config
must be at `secrets/auth/config.json.age` and its private key at `secrets/auth/age_key`
— those two filenames are what compose mounts.

### 3. Secrets

Every secret named in the compose `secrets:` block must exist before `up`, or Docker
refuses to start the containers.

Private keys (generated automatically by `scripts/crypto.ts` if missing):

| Key                          | Decrypts                        |
| ---------------------------- | ------------------------------- |
| `secrets/age_key_app`        | app + MySQL + tunnel secrets    |
| `secrets/auth/age_key`       | auth service config             |
| `secrets/watchtower/age_key` | auto-updater config + API token |

Plaintext inputs, one value per file, no trailing newline:

```
secrets/app/env/
  auth_crypto_cookies        random 32+ chars
  auth_server_location       hostname of the auth service
  auth_port_location         port of the auth service
  hmac_client_id             shared with the auth service
  hmac_shared_secret         shared with the auth service
  oauth_google_client_id
  oauth_google_client_secret
  oauth_github_client_id
  oauth_github_client_secret
  nuxt_turnstile_secret_key
  resend_api_key
  tunnel_token               Cloudflare tunnel token

secrets/app/mysql/
  mysql_root_password
  mysql_user
  mysql_password
  mysql_database

secrets/auth/config.dev.json    JSON config for the auth service
secrets/watchtower/config.dev.json
secrets/watchtower/api_token
```

The `*dev.json` files are encrypted to `*.json.age` by name substitution in
`encryptAppSecrets`. Note that `cleanupAppSecrets` intentionally keeps any file whose
name contains `dev`, so those two JSON files stay on disk in plaintext.

### 4. Domain and gateway

- `DOMAIN` appears in `docker-compose.yml` (as an environment value on `dashboard` and
  `caddy`) and is consumed by `secrets/caddy/Caddyfile` as
  `http://{$DOMAIN:localhost}`. Caddy speaks plain HTTP on purpose — TLS is terminated
  at Cloudflare, and the tunnel connects to Caddy on the private network.
- `secrets/caddy/sites/site` contains the full routing policy: which paths go to the
  app, which are served from the pre-rendered site, the cache headers, and the
  `@blocked` path list. Review it against your own routes.
- `secrets/caddy/utils/*` holds the rate-limit zones and the ban policy
  (`caddy_mib`). **These are tuned for my traffic.** The numbers are aggressive: 1000
  events/min per /24 on static assets, 5 contact submissions per hour per IP, and
  escalating bans after 4 rate-limit hits. Re-tune before pointing real users at it.
- `trusted_proxies static private_ranges` plus `client_ip_headers CF-Connecting-IP`
  assume Cloudflare. If you terminate elsewhere, change the header name or every rate
  limit will key on the proxy's IP and ban your whole user base at once.

### 5. Cloudflare tunnel

The `tunnel` container runs `cloudflared tunnel run` using `TUNNEL_TOKEN` decrypted at
startup from `secrets/app/env/tunnel_token.age`. You need a Cloudflare tunnel whose
public hostname points at `http://caddy:80` on the `frontend` network. Without a
tunnel token the container exits immediately and nothing is reachable from outside.

If you do not want a tunnel, delete the service and publish Caddy's port instead —
but then you own the inbound firewall rules yourself.

### 6. Turnstile keys

The **site key** is hardcoded in two places:

```ts
// apps/core/nuxt.config.ts and apps/static/nuxt.config.ts
turnstile: { siteKey: '0x4AAAAAADmgk9pVpmAk-PAy' },
```

Replace both with your own key from the Cloudflare dashboard, and put the matching
secret in `secrets/app/env/nuxt_turnstile_secret_key`. A site key only validates for
its own domain, so contact forms and the dashboard will fail captcha until you do this.

### 7. Email sender

The contact form sends through Resend with a hardcoded sender and recipient:

```ts
// apps/core/server/routes/contact.post.ts
from: 'noreply@riavzon.com',
to: 'sergo998826@gmail.com',
```

`noreply@riavzon.com` is **my domain**, verified in my Resend account. Sending with it
from your deployment will be rejected. Change both addresses to a domain you have
verified with Resend, and set `RESEND_API_KEY` to your own key. The auth service sends
its own mail (signup confirmation, password reset) from its own config — update that
too, or those flows will silently fail.

### 8. Grafana Alloy

`config.alloy` ships logs and metrics to **my** observability stack. Both endpoints are
mine, on my WireGuard mesh:

```hcl
loki.write "local_mesh" {
  endpoint { url = "http://10.10.10.1:3100/loki/api/v1/push" }
}

prometheus.remote_write "metrics" {
  endpoint { url = "http://10.10.10.1:9090/api/v1/write" }
}
```

Replace those with your own Loki and Prometheus endpoints. The `10.10.10.0/24`
network is my WireGuard mesh, and `docker/alloy/entry.sh` adds a route to it through
the `egress` gateway (`173.22.20.1` on `eth1`) — that also needs changing to match
your compose subnets.

The container intentionally mounts `/var/lib/docker`, `/var/log`, `/proc`, `/sys`, and
`/var/run/docker.sock`, and needs `cap_add: NET_ADMIN` plus the host's docker and
systemd-journal group GIDs (`988`, `4`). Those GIDs are distro-specific.

**If you do not want telemetry, remove the `alloy` service entirely.** It is not
required for the app to function.

### 9. cloud-init and WireGuard

`cloud-init.yml` is the provisioning file for my VM. It contains my mesh topology and
will not work as-is:

| What                                                           | Where                             | Action                                                                                      |
| -------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------- |
| `PrivateKey = {{ ds.config.user_wg_key }}`                     | `wireguard.interfaces[0].content` | DigitalOcean metadata placeholder — replace with your key or your own templating            |
| `PublicKey = JQIvBZQn...`                                      | same block                        | **My** mesh server's public key — replace                                                   |
| `Endpoint = 10.100.102.149:51820`                              | same block                        | My mesh relay — replace with your endpoint                                                  |
| `AllowedIPs = 10.10.10.10/32`                                  | same block                        | My gateway — replace                                                                        |
| `ListenAddress {{ ds.config.user_wg_ip }}`                     | `99-custom-server.conf`           | SSH binds **only** to this address                                                          |
| `AllowUsers sergio@10.10.10.10 restricteduser@10.10.10.10`     | same                              | Your users and your mesh IPs                                                                |
| `ssh_authorized_keys: {{ ds.config.user_ssh_pubkey }}`         | `users:`                          | Your public keys                                                                            |
| `ufw allow from 10.10.10.10 / from 10.100.102.149`             | `runcmd`                          | Your mesh IPs                                                                               |
| `-o enp5s0`                                                    | `/etc/ufw/after.rules`            | Your host's actual NIC name                                                                 |
| `sergio` / `restricteduser` names, `chpasswd: password: admin` | `users:`, `chpasswd:`             | Your users; the password is a placeholder — password auth is disabled, but change it anyway |

Two traps worth understanding before you copy this:

1. **SSH is bound to the WireGuard address.** If `wg-quick` fails, there is no SSH at
   all. On a cloud VM keep console access via the provider's web console, or add a
   second `ListenAddress` on the private VPC interface.
2. **`PostUp` rules run before Docker starts.** They reference the `DOCKER-USER` chain,
   which only exists once Docker is up. On a fresh boot the `iptables` calls can fail
   and the mesh routing silently does not apply. Re-run `wg-quick down wg0 && wg-quick up wg0`
   after Docker has started, or move the rules into a systemd unit ordered
   `After=docker.service`.

The `journald` drop-in caps the journal at 500 MB / 30 days, which matters because
Alloy reads `/var/log/journal`.

### 10. Registry and CI

`.github/workflows/deploy.yml` pushes to `ghcr.io/sergo706/*` using
`${{ secrets.GITHUB_TOKEN }}`. Fork it, change the image names in both the workflow and
`docker-compose.yml`, and note that the compose file has `pull_policy: never` on
`dashboard`, `migrations`, and `caddy` — they are expected to be built locally, not
pulled.

### 11. Auto-updater

`watchtower` polls every 300 s (`WATCHTOWER_POLL_INTERVAL`) and acts on containers
labelled `com.centurylinklabs.watchtower.enable=true` (`dashboard`, `caddy`).
`WATCHTOWER_REVIVE_STOPPED=true` means a container that crashed will be restarted by
the updater.

### 12. Refresh interval

`DATA_RESET_SCHEDULE` is in milliseconds and defaults to 24 h. It is passed to the
backup rebuild in `02.scheduler.ts`, which shells out to
`server/scripts/runDbUpdate.ts` and swaps the data directory atomically.

---

## Deployment

1. CI builds and pushes every image on push to `main`.
2. A host provisions itself from `cloud-init.yml` — Docker, the private network
   interface, UFW rules, and the restricted users.
3. Secrets are encrypted on the workstation and copied to the host.
4. `scripts/start-core.mts` brings the stack up.
5. The auto-updater polls the registry every 5 minutes and replaces containers that
   carry the update label.

Logs and metrics are collected by Grafana Alloy and pushed to a private Loki/Prometheus
pair over the private network.
